Thought process
This is really an architecture question about how far the scope will stretch. A few options worth considering:

Option A: Expand this repo and rename it. If the new file types share the same workflow (media transfer review, operator runs it against a submission folder, gets a report), then the scanning infrastructure you've already built — the venv management, reporting, logging, test harness, CI — is directly reusable. You'd rename to something like Scan-Submissions or Media-Transfer-Scanner, add detection logic that routes files to the right analyzer, and keep Python scanning as one module among several. This avoids duplicating all that plumbing.

Option B: New repo, new project. Makes sense if the other file types need fundamentally different tooling (different languages, different deployment model, different audience). But if it's still "operator points at a folder, gets a report," you'd end up rebuilding the same reporting, logging, and venv patterns from scratch.

Option C: Orchestrator + plugins. Keep Scan-Python-Packages as-is and create a parent project that discovers file types in a submission folder and dispatches to the right scanner. Each scanner is its own repo/module. This is the most flexible but also the most engineering overhead — you'd need to define a common finding format and report aggregation layer.

Given your setup — single operator, media transfer workflow, PowerShell 5.1 host — I'd lean toward Option A. You already have the hardest parts built (the PS 5.1 robustness patterns, the test infrastructure, the reporting). Adding a new file type scanner would look a lot like adding Invoke-BinaryInspection did: a new function, maybe a Python helper, new fixtures, and a few more lines in the report. The rename can happen when you're ready to broaden the scope.

The nice thing is these mostly fit into your existing pipeline with relatively small additions:

npm packages (.tgz, package.json) — closest to what you already have. You'd extract the tarball, run something like npm audit against the package.json dependencies (analogous to pip-audit), scan .js files with a linter or static analyzer for risky patterns (analogous to Bandit), and check for hardcoded secrets with detect-secrets which already handles JS.

PowerShell (.ps1, .psm1, .psd1) — you could use PSScriptAnalyzer for risky patterns (it's the PowerShell equivalent of Bandit), and detect-secrets already picks up hardcoded credentials in PS files.

Bash/shell scripts (.sh, .bash) — ShellCheck for static analysis, detect-secrets for credentials. You'd flag things like curl | bash, eval, and hardcoded IPs/URLs.

Disguised scripts (.txt, .log, etc.) — this is where your existing unsupported-file detection becomes a launching point. You'd add content-type sniffing (shebang lines, PowerShell signatures, script-like patterns) to flag files that are scripts hiding behind innocent extensions. That's a high-value detection because it's exactly what someone trying to sneak something through would do.

LLM files (model weights, configs) — this is the most specialized. You'd want to check for pickle-based serialization (which can execute arbitrary code on load), scan config files for suspicious URLs or API endpoints, and flag unexpected executable content embedded in model archives.

For the rename, I'd suggest something like Scan-MediaTransfer or Scan-Submissions — broad enough to cover all of these without needing another rename later.
